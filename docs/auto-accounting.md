# 自动记账与解析

## 1. 范围

自动记账负责把通知和短信转换为账单。主要入口：

- `service/LedgerNotificationListener.kt`
- `service/SmsReceiver.kt`
- `service/AutoLedgerIngestor.kt`

短信与通知只负责取得原始文本，后续去重、解析、自动入账判断、写库和结果通知都交给 `AutoLedgerIngestor`。

## 2. 统一入口

`AutoLedgerIngestor.process()` 执行以下步骤：

1. 构造 `NotifyRaw`。
2. 生成内存与数据库共用的通知去重 Key。
3. 检查进程内 Seen 缓存和持久化 `SeenStore`。
4. 通知走 `ParsePipeline.parse()`，短信走 `ParsePipeline.parseSms()`。
5. 命中 `autoRecord = false` 时只消费事件，不生成账单。
6. 调用 `LedgerRepository.addAutoParsed()`。
7. 更新通道最近入账时间。
8. 写入 Seen 记录并调用 `BillNotifier.notifyAdded()`。

## 3. 解析优先级

通知与短信共用的漏斗顺序：

1. 全局词库
2. 短信发送方闸门
3. 用户自定义规则
4. 系统规则
5. 内置解析兜底

### 3.1 全局词库

`ParsePipeline.evaluateGlobalVocabulary()` 先检查强制认账词，再检查忽略词。

- 命中强制词：继续解析，并把最终置信度设为 `1f`。
- 未命中强制词但命中忽略词：立即丢弃。
- 两者都未命中：进入下一层。

强制认账词高于忽略词。通知与短信入口都在任何规则之前执行这一层。

### 3.2 短信发送方闸门

短信通过全局词库后还要执行 `NotificationRules.isPlausibleSender()`。该闸门综合发送方和正文金融词，用于拦截 106 营销短信等高风险来源。

### 3.3 用户规则

`ParsePipeline.matchUserRule()` 只匹配 `creator = "user"` 的启用规则。命中后直接生成账单，不再运行系统规则。

### 3.4 系统规则

`ParsePipeline.matchSystemRule()` 只匹配 `creator = "system"` 的启用规则。系统规则由 `RuleSeed` 播种，用户只能启停，不能编辑或删除。

### 3.5 内置兜底

数据库规则全部未命中、规则为空或规则读取失败时，调用 `NotificationRules.parse()/parseSms()`。内置解析独立存在，避免规则表损坏导致自动记账整体失效。

## 4. 规则格式

规则存储在 Room `rule` 表。主要字段：

| 字段 | 作用 |
| --- | --- |
| `id` | 规则唯一键 |
| `app` | 包名或短信发送方；空值表示任意来源 |
| `type` | `notice`、`sms`、`ocr` |
| `creator` | `user` 或 `system` |
| `patternJson` | 金额、方向、阻断词、分类词等配置 |
| `enabled` | 是否参与匹配 |
| `autoRecord` | 命中后是否自动写入 |

规则 JSON 必须包含可验证的 `amount` 与 `direction` 能力。`RuleSafety` 会拒绝明显不安全的回溯正则。

规则引擎有三层保护：

1. 编译期检查 JSON 与正则安全性。
2. 单条规则总匹配预算为 100ms。
3. 超时或异常规则进入进程内熔断集合，本次进程生命周期内不再执行。

规则新增、编辑、启停或删除后，必须调用 `RuleEngine.invalidate()`。

“测试此规则”调用 `RuleEngine.previewRule()`，与真实规则共用编译和匹配逻辑。该预览只验证单条规则，不包含全局词库与分层漏斗。

## 5. Pending 订单

“下单”“待付款”等文本可能只是订单创建，不代表已扣款。

`ParsePipeline.settlePending()` 的处理：

1. 未支付订单且没有强制认账词时，只写入 `PendingMap`。
2. Pending 不进入 Room，也不发入账通知。
3. 5 分钟内出现同应用、同金额、同方向的支付确认后，合并分类、备注和卡号后四位。
4. 超时或没有确认的 Pending 静默丢弃。

## 6. 跨来源去重

### 6.1 数据库候选

`LedgerDaoSql.TIMED_MERGE_CANDIDATES` 只查询：

- 非周期模板。
- 非内部转账。
- 金额换算为分后完全相同。
- 收支方向相同。
- 时间差不超过 5 分钟。

候选通过 `timestamp BETWEEN since AND until` 限定范围，可以使用时间索引。

### 6.2 合并条件

`ParseDedup.shouldMerge()`：

- 时间差不超过 1 分钟时，直接合并。
- 时间差为 1 至 5 分钟时，要求一方为微信/支付宝，另一方为银行来源。
- 同源记录超过 1 分钟不合并。

银行短信来源可能只记录为“短信记账”，此时备注需要包含银行语义才能参与 1 至 5 分钟的跨源判断。

### 6.3 合并结果

`chooseMergeTarget()` 选择时间差最小的候选，时间差相同取较小 ID。

`mergeRecords()` 保留已有记录 ID 和 `externalId`，按以下信息量选择备注和分类：

- 备注长度。
- 是否包含卡号后四位。
- 主分类是否有效且不为“其他”。
- 是否存在子分类。
- 是否为银行来源。

来源以“ + ”追加并去重，例如“银行通知 + 微信通知”。合并成功后只保留一条账单。

### 6.4 短时重复投递

`ParseDedup.accept()` 还有一层内存去重：

- 指纹由金额分、规范化商户和秒级时间组成。
- 同一指纹 5 分钟内再次出现会丢弃。
- 同一“金额 + 商户”在 2 秒内再次出现会丢弃。

该层只用于通知和短信，不作用于手动记账、CSV 导入和 WebDAV 恢复。

## 7. 长期去重键

进程可能被系统或用户清理，因此 `SeenKeyEntity` 将短时去重键持久化到 `seen_key` 表。

- 默认保留 10 分钟。
- `HealthJobService` 定期清理过期键。
- 重复键写入会刷新最后出现时间。

## 8. 分类推断

`CategoryInference` 的优先级：

1. 商户精确映射，权重 100。
2. 强关键词，权重 80。
3. 弱关键词，权重 40。
4. 兜底“其他”，权重 10。

执行细节：

- 预处理 Unicode 规范化、小写化、空白压缩和支付平台前缀清理。
- 最长商户键优先。
- 排除词优先阻断规则。
- 正则词匹配使用字母数字边界，避免“交通”误伤“交通银行”。
- 最高权重并列时回退“其他”。
- 一级分类必须位于调用方允许列表中。

用户自定义二级分类只用于细化已命中的主分类，不能单独把未知文本提升成另一主分类。移除匹配到的子分类词后，剩余文本仍须命中同一主分类。

## 9. 周期账单

`RecurringWorker` 每天在 00:05 后检查周期模板。

- 支持每周、每月、每年。
- 模板记录 `isRecurring = true`，不参与统计。
- 实账使用 `is_recurring = false` 与 `source = "recurring"`。
- 唯一键由 `RecurringExternalIds.generate(templateId, calendar)` 生成。
- 手动创建周期账单与 Worker 必须共用这个函数。

## 10. 失败与可观测性

- 自动解析失败会记录 `AutoLedger` Logcat 标签。
- 规则加载失败会回退内置解析。
- 入账失败不会更新通道最近入账时间。
- 通知渠道关闭时账单仍会入库，但用户看不到结果与撤销按钮。
- 权限体检页显示通知与短信通道最近入账时间。

## 11. 修改自动记账时的检查项

- 是否保持全局词库最高优先级。
- 是否保持用户规则高于系统规则。
- 是否保留内置兜底。
- 是否使用分处理金额比较。
- 是否避免把同秒真实双笔误合并。
- 是否让规则预览复用真实引擎。
- 是否补充解析、去重、规则和转账相关测试。

## 12. 已知限制

- 跨源来源判断主要依赖 `source` 字符串，银行短信可能只显示为“短信记账”。
- 合并时按整行信息丰富度选择分类，个别字段可能来自不同记录。
- 规则预览不等同于完整解析漏斗。
- 自定义二级分类在无 `Context` 的纯推断调用中依赖已初始化的内存分类树。
