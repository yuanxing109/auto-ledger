## 2. 三个待决策项（不替你拍板）

### 决策 1｜氛围色系统（`GlassAmbience` + `glassHueDrag`）

现状事实：`GlassAmbience.hue`（默认 212°）/`energy` 是全局可变状态；`GlassHost`（`MainActivity:31` 唯一挂载点）用它给整页壁纸上色（`Color.hsv(hue,0.62,0.58)`，alpha 0.30×(0.4+energy)）；`glassHueDrag()` 挂在 Home OverviewCard 与 SettingsAmbienceCard 上，横拖改全局色相。

| 选项 | 做法 | 对 Home OverviewCard 的连带改动 | 对 SettingsAmbienceCard 的连带改动 |
|---|---|---|---|
| **A. 全站移除** | 删 `GlassAmbience` / `glassHueDrag` / `GlassHost` 氛围层；`GlassHost` 只留壁纸+压暗（或直接退化为纯色 `page`） | 必须重做：`Color.hsv(...)` tint 与 `glassHueDrag()` 同时删除，卡片改 `surface` + `border`；「横向拖动卡片可切换氛围色」文案删除；`White70/20/10/05`（基于 `onHero`）全部改 `text/textSecondary` 体系 | 整块删除（约 40 行），设置页少一项；`Brush.horizontalGradient` 彩虹条一并消失 |
| **B. 仅 Settings 保留** | `GlassAmbience` 只被 SettingsAmbienceCard 读写，Home 不再参与 | 删 tint + `glassHueDrag` + 提示文案；卡片不再随全局色变 | 保留拖动条与渐变，但语义变为"只影响设置页自身预览"，需改文案；若仍驱动全局 `GlassHost`，则 Home 也会被动变色 → **此选项要求把 hue 从全局降为设置页局部状态**，否则名不副实 |
| **C. 保留但降级为静态色** | `GlassAmbience` 固定为常量（如 212°），删除 `glassHueDrag` 与 `energy` 抖动 | 删除 `glassHueDrag` 与提示文案；tint 改为固定色或直接 `surface`；视觉可保留极轻色相 | 拖动条改只读展示或删除；彩虹 `Brush` 删 |

## 3. 优先级排序（正确性 > 交互 > 视觉）

### 8.1 radiusSmall 真实值核实

**V3 描述修正**：EntryRow 内块圆角由 `13.dp` 改为 `radiusSmall`（12dp），**视觉差为 1dp**，不是 5dp。若误用 `radiusSm`（8dp）才会产生 5dp 差异——该情况未发生。

### 9.3 13 个引用点的分类（按 WCAG 1.4.11 适用对象）

**纠正：WCAG 1.4.11「非文本对比度」3:1 只约束「理解内容所必需」的非文本视觉信息**——即可交互组件的边界、状态指示、焦点环。**装饰性卡片/容器的外框不在其约束范围内**，只要求「在深浅主题下肉眼可辨边界」，目标值可低于 3:1。

据此把 13 个引用点分两类。判定标准：**该 border 是否承担「让用户识别可点击区域」的职责**（即 border 所围合的容器本身是否 `clickable`）。

### 9.4 `.copy(alpha = x)` 机制核实（原表算错，已重算）

**纠正：`Color.copy(alpha = x)` 是替换 alpha，不是与原 alpha 相乘。** 上一版 §9.3 把 4 处派生引用按"相乘"计算（得到 6.7% 有效 alpha、1.15:1），**完全错误**。

实际机制：`border.copy(alpha = 0.55f)` → 渲染 alpha 直接为 **55%**，与 `border` 原 alpha（12.2%/20.0%）无关。

#### 重算结果（对各自填充底，非对 page）

| # | 文件:行 | copy 入参 | 实际渲染 alpha | 浅色合成 / 对比 | 深色合成 / 对比 | 判定 |
|---|---|---|---|---|---|---|
| 1 | `HomeScreen.kt:209` | `0.55f` | **55%** | rgb(118,122,131) / **4.10:1** | rgb(147,149,151) / **6.19:1** | ✅ 远超 3:1 |
| 2 | `SearchScreen.kt:484` | `0.55f` | **55%** | rgb(118,122,131) / **4.09:1** | rgb(146,148,151) / **6.20:1** | ✅ 远超 3:1 |
| 3 | `SearchScreen.kt:546` | `0.5f` | **50%** | rgb(130,134,142) / **3.49:1** | rgb(135,137,140) / **5.31:1** | ✅ 已达标 |
| 4 | `SearchScreen.kt:723` | `0.55f` | **55%** | rgb(118,122,131) / **4.10:1** | rgb(147,149,151) / **6.19:1** | ✅ 远超 3:1 |

**原表错误对照**：

| 项 | 原表（错误） | 正确值 |
|---|---|---|
| 机制 | 相乘：12.2% × 0.55 = 6.7% | 替换：直接 55% |
| `HomeScreen:209` 浅色对比 | 1.15 | **4.10** |
| `SearchScreen:546` 浅色对比 | 1.13 | **3.49** |
| 提 border 后是否受益 | "完全不受益" | **本来就不需要受益——它们已经达标** |

**重大结论翻转**：这 4 处派生引用**不是问题，反而已经是全项目对比度最高的 border 使用**（4.10 / 3.49 / 4.10 / 6.19，全部 ≥3:1）。上一版把它们当作"隐藏核心风险"是误判。

**真正的副作用**：这 4 处用 55% alpha 画 0.5dp 细线，比裸 `border`（12.2%）重 4.5 倍——**视觉层级倒挂**：chip 边框比卡片外框还显眼。若类别 I 的裸 border 提到 `0x77`（46.7%），两者才趋于一致（46.7% vs 55%），层级反而更合理。

### 9.5 按类别分别定值（替代原「方案 A/B 二选一」）

原方案 A（统一提 border）与方案 B（新增 `borderStrong`）都基于"追求统一 token 3:1"的前提。按 9.3 的分类，**这个前提不成立**：类别 II 的装饰性卡片本就不受 3:1 约束，没必要为它们把描边压重。

#### 定值方案

| 用途 | token | 浅色 | 深色 | 对比度 | 依据 |
|---|---|---|---|---|---|
| **类别 I** 可交互边界 | `border`（现 token 提值） | `0x1F` → **`0x77`** | `0x33` → **`0x62`** | surface 3.18/3.62，variant 3.00/3.01 | WCAG 1.4.11 硬要求 |
| **类别 II** 装饰性卡片 | `borderSoft`（**新增**） | **`0x1F`**（沿用原值） | **`0x33`**（沿用原值） | 1.29 / 1.88 | 仅需"可辨"，不需 3:1 |
| **类别 I 例外** 30dp 小圆 | 沿用 `borderSoft` | `0x1F` | `0x33` | 1.29 / 1.88 | 尺寸过小，3:1 会过重；优先修触摸尺寸 |
| 4 处 `.copy(alpha=0.5~0.55f)` | 不改 | — | — | 3.49~6.19 | **已达标**，但需评估视觉层级倒挂 |

#### 与旧方案的差异

| 项 | 旧方案 A | 旧方案 B | 新方案（按类别） |
|---|---|---|---|
| 前提 | 统一提 border 到 3:1 | 新增 borderStrong 服务卡片 | **分类**：可交互提、装饰性不提 |
| token 改动 | 1 个值 | 新增 1 个 token + 4 个别名 | **新增 1 个 `borderSoft` + `border` 提值** |
| 卡片视觉 | 全部变硬 | 卡片用 strong，chip 用淡 | **卡片保持现状（软）**，chip/选项卡变清晰 |
| 30dp 小圆 | 过重 | 保持淡 | 保持淡（并建议修尺寸） |
| 工作量 | 改 2 行 | 改 data class + 转发 + 逐页归类 | 改 data class + 转发 + **逐页归类（必做）** |

#### 实施注意

1. **必须先逐页归类再改值**，否则 9 处直接引用会被一刀切。
2. `borderSoft` 需加进 `LedgerColors` data class、`LedgerTheme.kt` 转发、`SettingsUi.kt:103` / `ReportScreen.kt:103` 的 `CardBorder` 别名改指向。
3. 4 处 `.copy(alpha=0.5~0.55f)` 是否要降到 `borderSoft.copy(alpha=0.3f)` 以恢复层级，需真机对比后定。
4. `ReportScreen:226` 的 30dp 触摸目标（A7/A8）**优先级高于**其描边对比度，应另开一轮。

### 9.6 本轮结论

**未改 `LedgerPalette.kt`，未改任何 `.kt` 文件。** 仅修正文档中的分类与对比度计算。

修正内容：
1. WCAG 1.4.11 适用范围收窄到类别 I（可交互边界），装饰性卡片不强制 3:1。
2. `.copy(alpha=)` 按替换机制重算，4 处派生引用实际 3.49~6.19:1，**已达标**（原表误算为 1.13~1.15:1）。

### 12.5 Step 5｜GlassDialog 遮罩核查

#### 现状

- `GlassDialog` 内**无显式遮罩**，遮罩由 `Dialog` 系统默认 `dimAmount` 承担。
- 项目 `themes.xml` **未覆盖 `android:backgroundDimAmount`**（grep `dimAmount` 无结果），故走系统默认 **0.6（60% 纯黑）**。
- `LedgerColors.scrim`（浅 `0x990B1220` / 深 `0xB30B1220`）已定义但**全项目零引用**。

#### 量化对比

| 主题 | 系统默认 60% 纯黑 | 设计 scrim | 差值 |
|---|---|---|---|
| 浅色 | `rgb(98,99,100)` | `0x99#0B1220` = `rgb(105,110,120)` | R +7 / G +11 / B +20 |
| 深色 | `rgb(4,6,8)` | `0xB3#0B1220` = `rgb(11,17,28)` | R +7 / G +11 / B +20 |

系统 scrim 是**纯黑 60%**；设计 scrim 是**近黑蓝 60%/70%**，多一层冷色调（B 通道高 20）。

#### 判断

**视觉上基本一致，无需改动。** 理由：

1. 浅色下两者合成色差 ΔE 极小（R/G/B 差 7/11/20，在 100 灰阶上肉眼几乎不可辨）。
2. 深色下系统 60% 纯黑合成 `rgb(4,6,8)` 已接近纯黑，设计 scrim `rgb(11,17,28)` 同样极暗，差异被暗部压缩。
3. **若叠加会过深**：系统 60% + 设计 0x99 = 合成 alpha **0.84**（浅色）/ **0.881**（深色），远超设计意图，弹窗后内容会完全不可见。
4. 设计 scrim 的「冷色调」价值在遮罩层几乎无感——遮罩的目的是压暗而非表达品牌色。

**结论：无需改动 GlassDialog.kt。** `LedgerColors.scrim` 保留定义，供未来 `ModalBottomSheet` 或自定义遮罩场景使用；若将来要覆盖系统 `dimAmount`，可在 `themes.xml` 加 `<item name="android:backgroundDimAmount">0.55</item>` 并改用显式 scrim Box——但那是设计决策，不是本轮缺陷。

#### 现状统计

| `GlassKit.kt:261` | `RoundedCornerShape(50)` |

**共 14 处。** 其中 `RoundedCornerShape(50.dp)` 形式 **0 处**（全是无单位 `50`，因为 `50` 会被推断为 `Int` → `Dp` 扩展？实际是 `RoundedCornerShape(percent: Int)` 重载，即 50% 圆角）。

#### 关键发现：这不是 50dp，是 50%

`RoundedCornerShape(50)` 调用的是 **`RoundedCornerShape(percent: Int)`** 重载，语义是「**圆角的 50%**」，即把矩形切成胶囊/椭圆——**不是 50dp**。

而 `LocalDimens.current.radiusCapsule = 50.dp` 是 **50dp 固定值**。

两者在大多数元素上视觉相同（因为元素高度 < 100dp 时 50% 圆角 ≈ 胶囊），但**语义不同**：

| 写法 | 语义 | 在 40dp 高按钮上 | 在 200dp 高元素上 |
|---|---|---|---|
| `RoundedCornerShape(50)` | 50% | 圆角 20dp | 圆角 100dp（全圆） |
| `RoundedCornerShape(50.dp)` / `radiusCapsule` | 固定 50dp | 圆角 50dp（会被裁成胶囊） | 圆角 50dp |

#### 回答三个问题

**Q1：有多少处？** → **14 处**，全部是 `RoundedCornerShape(50)`（百分比重载），**0 处**是 `50.dp`。

**Q2：应该走 `radiusCapsule` 还是保留字面量？**

**保留字面量。** 理由：
- `RoundedCornerShape(50)` 是**百分比语义**，`radiusCapsule` 是**固定 dp 语义**，二者不等价。
- 当前所有用法（顶栏胶囊、底部导航、chip、日期 pill）元素高度都 < 100dp，50% 与 50dp 视觉等价。
- 但若改成 `radiusCapsule`（50dp），未来若出现高度 > 100dp 的胶囊元素，圆角会突然从「全圆」变成「50dp」，视觉断裂。
- **百分比写法在胶囊场景是更正确的表达**：它保证无论元素多高都保持胶囊形。

**Q3：若改成 `radiusCapsule`，R6 是否应移除 `50.dp` 豁免？**

**不应该移除豁免，但也不该需要它。** 因为：
- `RoundedCornerShape(50)` 不匹配 R6 正则 `RoundedCornerShape\([0-9]+\.dp`（**没有 `.dp` 后缀**），本来就不被统计。
- R6 正则里的 `50\.dp` 豁免项是**多余的** —— 项目里根本没有 `RoundedCornerShape(50.dp)`。
- 建议：**保留 `50\.dp` 豁免**（无害，防未来有人写 `50.dp`），但**不把 `RoundedCornerShape(50)` 改成 `radiusCapsule`**。

**结论：本轮不改（14 处 > 5 处阈值），记 TODO-34。** 且需在 docs/09 补充说明「`RoundedCornerShape(50)` 是百分比语义，与 `radiusCapsule` 不等价」。

#### 为支持「撤销」新增的 API

```kotlin
// HomeViewModel
fun restoreEntry(entry: LedgerEntry) {
    viewModelScope.launch(Dispatchers.IO) { LedgerRepository.restore(context, entry) }
}

// LedgerRepository
suspend fun restore(context: Context, entry: LedgerEntry) {
    dao(context).insertAll(listOf(entry))   // 用 insertAll 保留原 id
    LedgerWidgetProvider.requestUpdate(context)
}
```

`deleteEntry` 是异步的，撤销时用删除前捕获的 `val removed = entry` 写回，`insertAll` 的 `OnConflictStrategy.IGNORE` 保证不产生脏数据。

## 20. restore 竞态修复、TODO-44 清零、reduce motion

### 20.1 Step 1｜restore 竞态核实

#### 现状实现

```kotlin
// HomeViewModel
fun deleteEntry(id: Long) {
    viewModelScope.launch(Dispatchers.IO) {          // launch，返回 Unit，调用方无法等待
        LedgerRepository.delete(context, id)          // 按 id 删
        extraPages.update { list -> list.filterNot { it.id == id } }
    }
}
fun restoreEntry(entry: LedgerEntry) {
    viewModelScope.launch(Dispatchers.IO) { LedgerRepository.restore(context, entry) }
}

// DAO
@Insert(onConflict = OnConflictStrategy.IGNORE)     // IGNORE，不是 REPLACE
suspend fun insertAll(entries: List<LedgerEntry>): List<Long>
```

#### 逐条回答

**Q1**：`deleteEntry` 是 **`launch`**（返回 `Unit`，调用方无法等待）；**按 id 删**（`deleteById(id)`）；`restoreEntry` 内部也是 `launch`；`insertAll` 冲突策略是 **`IGNORE`**。

**Q2 时序分析**：存在两种竞态。

| 场景 | 时序 | 后果 |
|---|---|---|
| **A. restore 早于 delete 完成** | delete 还在 IO 队列 → restore 先执行 `insertAll` | 记录**还在库里**，id 冲突 → `IGNORE` **静默丢弃** restore → 随后 delete 完成，**把记录删掉**。用户点了撤销，记录仍丢失，且无任何提示 |
| **B. delete 早于 restore** | 正常顺序 | 正常工作 |

**结论：场景 A 是真实 Bug。** `deleteEntry` 与 `restoreEntry` 各自在不同 `viewModelScope.launch` 里，**无任何顺序保证**，在同一 `Dispatchers.IO` 线程池上竞争。

**Q3 三个方案**：

| 方案 | 做法 | 优 | 劣 |
|---|---|---|---|
| **A** | `restoreEntry` 改 `REPLACE` + `deleteEntry` 改 `suspend` 并 await | 双保险 | `insertAll` 被 `addImported` 等多处复用，改 REPLACE 会影响去重逻辑 |
| **B** | 撤销用新 id 插入 | 避开 id 冲突 | 记录 id 变了；`deleteById` 用旧 id，若 delete 后完成则删不到，**反而制造新 Bug** |
| **C** | `deleteEntry` 返回 `Deferred`，调用方 `await()` 后再弹 Snackbar | **从根上消除竞态**；保留 `IGNORE` 防重复语义 | 用户点删除到 Snackbar 弹出有 IO 延迟（<10ms，无感） |

**推荐并已执行：C。**

### 20.3 Step 3｜restore 竞态修复（方案 C）

```kotlin
// HomeViewModel：deleteEntry 改返回 Deferred
/**
 * 删除账目，返回的 Deferred 在删除**真正落库后**才完成。
 *
 * 调用方（Snackbar 撤销流程）必须先 await 再弹提示：
 * 否则用户可能在 delete 尚未完成时点撤销，restoreEntry 的 insert 会被

fun deleteEntry(id: Long): Deferred<Unit> = viewModelScope.async(Dispatchers.IO) {
    LedgerRepository.delete(context, id)
    extraPages.update { list -> list.filterNot { it.id == id } }
}
```

### 20.4 Step 4｜reduce motion 降级


#### 为何不用 `LocalMotionDurationScale`

首次尝试 `LocalMotionDurationScale.current.scaleFactor` + `CompositionLocalProvider` 注入，**编译失败**——该 API 在 Compose 1.12 里不是公开符号（`Unresolved reference`）。回滚后改用 `android.animation.ValueAnimator.getDurationScale()`（Android 框架 API，读的正是同一个系统设置 `Settings.Global.ANIMATOR_DURATION_SCALE`）。

**副作用**：`getDurationScale()` 是进程级静态值，只在 App 启动时读一次（`remember {}`）。运行期间切换系统开关需重启 App 生效——可接受（改开关本身要离开 App）。

| 动画 | 是否受控 |
|---|---|
| `LedgerApp` 覆盖层 `AnimatedContent`（fade 200ms） | **已降级为 0ms** |
| `LedgerApp` 三页签 `AnimatedContent`（fade 160/120ms） | 未改（`tween` 固定值） |
| 底部导航 `animateFloatAsState` spring | 未改（Compose 内部已尊重 `durationScale`，自动瞬时） |
| `InteractiveHighlight` spring | 未改（同上） |

**说明**：Compose 的 `spring`/`tween` 默认已乘 `LocalMotionDurationScale`，系统关闭动画时本就会自动瞬时。本轮显式判断的价值是把 `tween(0)` 写死，即使某些 Compose 版本未乘 scale 也能保证瞬时——**冗余保险**。

### 21.10 TODO-48 执行记录（通知 + 撤销）

#### Step 1｜`ConfirmEntryReceiver` 发通知 + 撤销

```kotlin
scope.launch {
    try {
        val newId = runCatching { LedgerRepository.add(context, entry) }
            .onFailure { Log.w(TAG, "截屏记账入库失败", it) }
            .getOrDefault(-1L)
        manager.cancel(ScreenshotCaptureService.RESULT_ID)
        if (newId > 0L) showConfirmed(context, manager, entry, newId)
        else Log.w(TAG, "截屏记账未入库（失败或被 IGNORE），不发通知")
    } finally { pending.finish() }
}
```

`showConfirmed` 关键点：

| 项 | 实现 |
|---|---|
| 权限检查 | `NotificationManagerCompat.from(context).areNotificationsEnabled()`，无权限 → Toast「已入账」后 return |
| channel | `BillNotifier.ensureChannel(context)` 复用 `auto_ledger_bill` |
| 通知 id | `CONFIRMED_ID = ScreenshotCaptureService.RESULT_ID + 1`（**固定值**，连续截图覆盖不堆积） |
| 撤销 PendingIntent | `getBroadcast(..., REQ_UNDO, Intent(...UndoBillReceiver).setAction(ACTION_UNDO).putExtra(EXTRA_ENTRY_ID, entryId).putExtra(EXTRA_NOTIFY_ID, CONFIRMED_ID), FLAG_UPDATE_CURRENT or FLAG_IMMUTABLE)` |
| 标题/正文 | 「已入账」/「${category} ¥ %,.2f」 |
| action | `addAction(0, "撤销", undoPending)` |
| 兜底 | `runCatching { manager.notify(...) }` 失败只记日志，不 crash |

**删除原 Toast「已入账」**（仅保留无通知权限时的 fallback）。

#### Step 2｜`UndoBillReceiver` 新增 `entry_id` 分支

两条链路共存，按 extra 分流：

```kotlin
val entryId = intent.getLongExtra(EXTRA_ENTRY_ID, -1L)
if (entryId > 0L) { undoByEntryId(context, intent, entryId); return }   // 截图记账链路
val externalId = intent.getStringExtra(EXTRA_EXTERNAL_ID).orEmpty()     // 自动记账链路（原逻辑不动）
```

`undoByEntryId`：`LedgerRepository.delete(context, entryId)` + `manager.cancel(EXTRA_NOTIFY_ID)` + Toast「已撤销这笔截图记账」/「这笔账单已不存在」。

新增常量：`EXTRA_ENTRY_ID = "entry_id"`。
